## Ejercicio 1.3. Las formas normales

### 1. Forma normal de cada tabla en el esquema actual

* **1FN (Primera Forma Normal):** todas las tablas del esquema tienen atributos con valores atómicos (sin listas ni valores múltiples en una misma celda) y cuentan con clave primaria definida.
* **2FN (Segunda Forma Normal):** las tablas con clave primaria compuesta (`PersonaTeléfono`, `ClienteCorreo`, `ProveedorCorreo`, `Categoria`, `Inventario`, `Surtir`, `Incluir`) no presentan dependencias parciales de atributos no clave sobre parte de la clave; sin embargo, en `Categoria` la clave compuesta `(Cod_Barra, Identificador)` junto con `Nombre` mezcla la entidad de categoría con la relación producto-categoría.
* **3FN (Tercera Forma Normal) y BCNF:** las tablas `Persona`, `Cliente`, `Empleado`, `Proveedores`, `PersonaTeléfono`, `ClienteCorreo`, `ProveedorCorreo`, `Productos`, `Inventario`, `Surtir` e `Incluir` cumplen 3FN y BCNF (en cada dependencia funcional no trivial, el lado izquierdo es clave o superclave).
  * **Tabla que incumple 3FN:** `Venta`, debido a que `Empleadoventas` depende transitivamente de `Ticket` a través de `Identificador_empleado` (`Ticket → Identificador_empleado → Empleadoventas`), duplicando información asociada al empleado.

### 2. Transformación a 3FN y comprobación de BCNF

1. **En `Venta`:** se elimina la columna `Empleadoventas` para suprimir la dependencia transitiva `Ticket → Identificador_empleado → Empleadoventas`. La relación con el empleado se conserva mediante `Identificador_empleado` (clave foránea a `Empleado`).
2. **En `Categoria`:** se crea la tabla catálogo `Categoria_Catalogo(Id_Categoria, Nombre)` para almacenar una sola vez cada categoría y se relaciona con `Categoria` mediante clave foránea, evitando repetir `Nombre` en cada fila de producto-categoría.
3. **Comprobación de BCNF:** tras eliminar `Empleadoventas` de `Venta` y normalizar `Categoria`, cada determinante en las dependencias funcionales no triviales es clave o superclave en su tabla respectiva. No se pierden dependencias funcionales del negocio al permanecer las claves y referencias correspondientes, por lo que el esquema queda en **3FN y BCNF**.

### 3. Reunión sin pérdida y preservación de dependencias

* **Reunión sin pérdida (prueba de atributos comunes):** al descomponer una tabla en dos relaciones y reunirlas por sus atributos en común, no se generan tuplas espurias cuando el conjunto de atributos comunes es clave en al menos una de las dos relaciones resultantes.
  * Al enlazar `Venta` con `Empleado` mediante el identificador del empleado, dicho atributo es clave en `Empleado` (y en `Persona`), por lo que la reunión natural conserva exactamente las filas reales.
  * Al enlazar `Categoria` con `Categoria_Catalogo` por el identificador de categoría, ese identificador es clave primaria en `Categoria_Catalogo`, asegurando que no se produzcan combinaciones falsas.
* **Preservación de dependencias:** las dependencias funcionales del negocio quedan contenidas dentro de las tablas resultantes, permitiendo validar las reglas del dominio sin depender de uniones adicionales para cada regla.

### 4. Migración sobre la base poblada (`migraciones/001-normalizacion.sql`)

La migración se ejecuta sobre la base ya poblada dentro de una transacción, trasladando los valores existentes a la nueva estructura sin reingresar datos manualmente:

```sql
BEGIN;

ALTER TABLE Venta
    DROP COLUMN IF EXISTS Empleadoventas;

CREATE TABLE IF NOT EXISTS Categoria_Catalogo (
    Id_Categoria VARCHAR(50) PRIMARY KEY,
    Nombre VARCHAR(50) NOT NULL
);

INSERT INTO Categoria_Catalogo (Id_Categoria, Nombre)
SELECT DISTINCT Identificador, Nombre
FROM Categoria
ON CONFLICT (Id_Categoria) DO NOTHING;

ALTER TABLE Categoria
    ADD CONSTRAINT fk_categoria_catalogo
        FOREIGN KEY (Identificador) REFERENCES Categoria_Catalogo (Id_Categoria)
        ON DELETE RESTRICT ON UPDATE CASCADE;

ALTER TABLE Categoria
    DROP COLUMN IF EXISTS Nombre;

COMMIT;
```
